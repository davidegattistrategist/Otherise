# Otherise — istruzioni per Claude

App per personal trainer: staff (titolare + collaboratori) gestisce clienti, programmi, check corporei, sessioni PT, posturale, pagamenti e diari settimanali; il cliente vede il proprio percorso e registra il logbook. Ogni personal trainer ha **la propria installazione** (proprio GitHub, Supabase, Vercel, chiave Anthropic). Interfaccia e testi **in italiano**; chi la usa non è tecnico.

## Stack
- Next.js 16 App Router (`src/app`), React 19, Tailwind 4, TypeScript. **Leggi `node_modules/next/dist/docs/` prima di usare API di Next**: `proxy.ts` sostituisce il middleware, `params`/`searchParams`/`cookies()` sono Promise.
- Supabase (Postgres + Auth) con `@supabase/ssr`. Client: `src/lib/supabase/{server,browser,admin}.ts`. `admin` usa la service role e salta i permessi: usalo solo lato server e solo quando serve (inviti, notifiche, cron).
- Anthropic SDK per l'assistente (`src/lib/ai/`), structured outputs JSON.
- Test: Vitest (`src/lib/lib.test.ts`, calcoli), test di permessi su DB vero (`tests/integration`), Playwright (`tests/e2e`).

## Comandi
- `npm run dev` · `npm run build` · `npm run typecheck` · `npm run lint` · `npm test`
- `npm run test:integration` (serve un Supabase di prova VUOTO: variabili `TEST_SUPABASE_URL`, `TEST_SUPABASE_ANON_KEY`, `TEST_SUPABASE_SERVICE_KEY`)
- Dati finti per prove: `npx tsx scripts/seed-demo.ts` su un database di prova vuoto (mai su quello vero)
- Tipi del database: `npx supabase gen types typescript --project-id <id> --schema public > src/lib/supabase/database.types.ts`

## Regole importanti
- **Permessi nel database (RLS)**, non solo nell'interfaccia. Funzioni helper in SQL: `is_owner()`, `is_staff()`, `can_manage_client(id)`, `is_client_self(id)`, `my_client_id()`. Il collaboratore vede solo i clienti con `coach_id` = lui; solo il titolare vede pagamenti, impostazioni, collaboratori.
- Stato del cliente (`clients.status`, card "Percorso" nella Scheda, azione `setClientStatus`): `active`; `paused` = in pausa, usa l'app come sempre ma esce da pagamenti da incassare, promemoria e previsioni; `archived` = percorso terminato (ex cliente): `is_client_self()` vale solo per chi non è `archived`, quindi niente programmi, misure, logbook, diario, pagamenti; gli resta la chat (`is_client_self_any()` per messaggi e consensi) e l'account. Pagine del percorso del cliente con `requireActiveClient()` (rimanda alla chat). Cliente gratis: `clients.free` (solo titolare), fuori da pagamenti, incassi, previsioni, export. Elenchi dei clienti in ordine di cognome e con il cognome davanti (`bySurname`, `listName` in `src/lib/names.ts`); le intestazioni restano "Nome Cognome".
- Il cliente **non deve mai vedere**: note delle sessioni PT (`pt_sessions`), `checks.notes_next_phase`, note private, bozze, valutazioni posturali non visibili. I check li legge solo con la funzione `my_checks()`.
- Il ruolo di un nuovo utente lo decide il trigger `handle_new_user` (primo utente = titolare; email in `staff_invites` = collaboratore; email di un cliente = cliente; altrimenti `none`). Mai fidarsi di dati inviati dal browser per il ruolo. Link per entrare preparato dal trainer (se l'email non arriva): `inviteLinkAction` in `src/app/staff/clienti/actions.ts` → pagina `/auth/entra` con un pulsante (così l'anteprima del link in chat non consuma il codice) → `/auth/confirm` → `/imposta-password`. Email sbagliata in un invito mai usato: `dropUnusedAccount` (stesso file) toglie l'account con l'email vecchia quando la scheda cambia email (`updateClientAction`) o si rimanda l'invito/link; "Rimanda l'invito" e "Prepara il link" usano l'email scritta in quel momento nella scheda anche se non salvata (`TypedEmail`, campo `data-client-email`, `saveTypedEmail`).
- **Modifiche al database**: mai cambiare migrazioni già eseguite. Aggiungi un nuovo file `supabase/migrations/AAAAMMGGhhmmss_descrizione.sql`, aggiorna i tipi, aggiungi/aggiorna i test di permesso, e **di' all'utente** che deve eseguire quel file nel SQL Editor di Supabase.
- Nessun dato reale di clienti nel codice, nei test o nei commit: solo persone inventate.
- All'assistente AI non si mandano nome, cognome, email o telefono del cliente (`src/lib/ai/context.ts`).
- Testi per l'utente: italiano semplice, dare del tu, niente gergo tecnico. Messaggi d'errore che dicono cosa fare.

## Dove stanno le cose
- Programma = JSON in `programs.content`: giorni → blocchi (`single`, `superset`, `circuit`, `amrap`, `emom`, `interval`, `text`) → esercizi con una prescrizione per settimana. Schema e helper in `src/lib/program/types.ts`. Gli id (nanoid) restano stabili: il logbook (`workout_logs`, `exercise_logs`) si aggancia a `day_id` e `item_id`.
- Prescrizioni ("4x8 60kg", "3x30\"") → `src/lib/program/prescription.ts`; righe del logbook → `logbook.ts`; calendario fasi → `schedule.ts`; nuova fase dal logbook → `next-phase.ts`.
- Pliche e composizione corporea: `src/lib/body/skinfolds.ts`. Uomo Jackson-Pollock 7 pliche; donna 5 pliche (senza pettorale e ascellare) riportate a 7 (×7/5) nella formula JP7 femminile; Siri. Se manca una plica si usa una formula validata a 3 pliche (`FORMULAS`); una plica mancante non vale mai zero e senza formula valida non si calcola la percentuale. Ogni cliente ha una **formula di riferimento** (`referenceFormula`: scelta dal trainer in `clients.skinfold_formula`, altrimenti la più completa valida in tutti i check) e la % salvata nei check (`body_fat_formula`) la segue sempre: dopo ogni salvataggio/eliminazione/cambio formula si chiama `recomputeClientChecks` (`src/lib/data/checks.ts`). Dopo 3 check di fila con una plica in più si propone una formula più completa (`formulaUpgrade`), solo col consenso del trainer. Pagina check dello staff: grafico % con formula a scelta, grafico pliche (somma comune o singola), formula di riferimento. Massimale stimato: tabella RPE in `src/lib/strength/e1rm.ts`.
- Pagamenti (fuori dall'app, qui solo il registro): `src/lib/billing.ts`, funzioni SQL `client_billing()` e `billing_overview()`.
- Diario settimanale (si chiamava check-up: tabella `checkins`, pagine `/cliente/diario` e `/staff/clienti/[id]/diario`, i vecchi indirizzi `/checkup` rimandano lì con i redirect in `next.config.ts`, migrazione `20261013100000_diario.sql` per titoli e link delle notifiche): soglie di avviso nella funzione SQL `flag_checkin` (voto ≤ 2, calo di 2 punti, richiesta scritta).

## Prima di dire "fatto"
`npm run typecheck && npm run lint && npm test && npm run build`. Se tocchi permessi o SQL, anche i test di integrazione. Se tocchi pagine, aprile nel browser (anche a larghezza telefono, 390px) e lancia i test end-to-end (`npx playwright test`, progetti "pc" e "telefono"; servono i dati di `scripts/seed-demo.ts`).
**Impaginazione**: se tocchi pagine o componenti, prima di dire fatto fai girare `scripts/stress-demo.ts` + `node scripts/layout-audit.mjs` (deve uscire senza segnalazioni) e guarda le pagine cambiate a 390 px e a 1280 px; poi rifai il seed per gli e2e. Mai `truncate`/`line-clamp` su nomi, titoli o prescrizioni (solo anteprime, con `data-clamp-ok`); niente `input` per testi che possono essere lunghi (usa una `textarea`, cresce da sola).
Le stesse schermate hanno spesso due versioni (telefono e computer) nascoste con le classi `md:hidden` / `hidden md:block`: nei test usa `.filter({ visible: true })`.
